# run-harness — 허들링 디자인 하네스 오케스트레이터

메인 Claude 세션이 이 절차를 직접 수행합니다. 각 Phase의 작업은 서브에이전트에게, 판정은 `judge`에게 맡깁니다.
작업 에이전트는 파일을 직접 쓰지 않고 산출물을 `=== FILE: … ===` 블록으로 **반환**합니다. (서브에이전트의 파일 쓰기가 Claude Code에서 막히는 문제로 2026-09-26 방법 2로 변경)
오케스트레이터는 그 블록을 **한 글자도 고치지 않고 저장만** 합니다. 내용을 직접 작성하거나 고치지 않습니다.

## 기준 문서

| 파일                  | 역할                                                        |
| --------------------- | ----------------------------------------------------------- |
| `story-service.md`    | 무엇을 위한 일인지 (유저스토리 US-1~5, ★ 어기면 안 되는 것) |
| `story-work.md`       | 실제로 어떻게 하는지 (①~⑦ 작업 흐름)                        |
| `harness/rules.yaml`  | **규칙 SSOT** — 게이트 판정 수치의 유일한 기준              |
| `prd.md`, `design.md` | 사람이 읽는 제품·디자인 설명 문서                           |

## 0. 시작

1. 사용자 요청에서 **화면 주제**를 뽑습니다. (예: "내 자산 등록 화면 하네스 돌려줘" → `내 자산 등록`)
   - 주제가 없으면 물어봅니다.
2. 주제를 영문 kebab-case **slug**로 정합니다. (예: `my-asset-register`)
   - `runs/` 아래 같은 주제의 기존 실행이 있으면 그 slug를 씁니다 → **재개**
3. `runs/<slug>/state.json`이 **없으면 (첫 실행)**
   - **Figma 파일 링크를 사용자에게 물어봅니다.** (링크 없이는 진행하지 않습니다)
   - `harness/defaults.yaml`에서 값이 `미정`인 항목(예: 탭 4개의 이름)이 있으면 함께 물어봅니다. 사용자가 답하면 동의를 받아 `defaults.yaml`의 해당 값을 고칩니다.
   - 받은 뒤 실행 요약(주제 · slug · Figma 링크 · 정한 기본값 · P1부터 시작)을 보여주고 확인을 받습니다.
   - `node harness/scripts/verify.mjs init <slug> --topic "<주제>" --figma <URL>`
4. `state.json`이 **있으면 (재개)**
   - `node harness/scripts/verify.mjs status <slug>` 결과를 보여주고 `next` 게이트부터 이어갑니다.
   - 종료 코드 3(🛑 차단)이면 **아무것도 진행하지 말고** 7번 보고로 갑니다.
   - **재개한 게이트의 산출물이 이미 폴더에 있으면 에이전트를 부르기 전에 `judge`부터 실행**합니다. 통과하면 에이전트 없이 다음 게이트로 갑니다 (예: 다시 연 실행의 P3 시안·컨펌).
5. 완료된 실행을 고치거나 확장해야 하면 사용자 동의를 받아 `node harness/scripts/verify.mjs reopen <slug> --from <gate>`로 다시 엽니다 (산출물은 유지).

## 1. Phase 루프

`state.json`의 `next` 값에 따라 아래를 반복합니다. 매 게이트 후 `state.json`을 다시 읽습니다.

| next          | 작업 에이전트      | 편집 폴더                                             | 이어서                |
| ------------- | ------------------ | ----------------------------------------------------- | --------------------- |
| `p1`          | `researcher`       | `runs/<slug>/p1-research/`                            | `judge` → p1          |
| `p2`          | `spec-writer`      | `runs/<slug>/p2-spec/`                                | `judge` → p2          |
| `p3`          | `concept-designer` | `runs/<slug>/p3-concept/` (approval.md 제외)          | `judge` → p3          |
| `p3-approval` | 👤 **사람**        | `runs/<slug>/p3-concept/approval.md`                  | `judge` → p3-approval |
| `p4`          | `builder`          | `runs/<slug>/p4-system/` (시스템 확장: 토큰·컴포넌트) | `judge` → p4          |
| `p5`          | `flow-designer`    | `runs/<slug>/p5-flow/` (verify-report.md 제외)        | `judge` → p5          |

작업 에이전트를 부를 때 전달할 것:

- `slug`, 화면 주제, Figma 파일 링크(P3·P4)
- 복귀로 다시 부르는 경우: `state.json` history의 **마지막 실패 사유** (P5는 `p5-flow/verify-report.md`도)
- "파일은 직접 쓰지 말고 `=== FILE: runs/<slug>/<phase 폴더>/<파일명> ===` 블록으로 반환할 것"

### 반환 블록 저장 (작업 에이전트가 끝난 직후, judge 호출 전)

1. 응답에서 `=== FILE: <경로> ===` ~ `=== END FILE ===` 블록을 모두 찾습니다.
2. 경로 검사 — 아래에 해당하면 **저장하지 않고** 사용자에게 보고합니다.
   - 현재 Phase 폴더(`runs/<slug>/p1-research/` 등) 밖의 경로
   - `approval.md`, `verify-report.md`, `state.json`
3. 통과한 블록은 내용을 **그대로** Write로 저장합니다. 요약·수정·서식 정리를 하지 않습니다.
   - 반환이 커서(수십 KB) Write로 옮기기 어려우면, 반환 텍스트를 파일로 두고 `node harness/scripts/save-blocks.mjs <slug> <파일>`로 저장합니다. guard-write와 같은 경로 규칙을 검사하고, 거부된 블록이 하나라도 있으면 아무것도 저장하지 않습니다.
4. 필수 파일 블록이 빠졌으면 저장하지 말고 같은 에이전트에게 빠진 파일만 다시 요청합니다.
5. 저장한 파일 목록을 사용자에게 한 줄로 보고한 뒤 `judge`를 부릅니다.

`judge`를 부를 때 전달할 것: `gate`, `slug`. P3·P4·P5에서는 judge가 Figma 실제 상태와 export를 지문으로 대조한 뒤 판정합니다 (Figma 읽기만). judge의 보고에서 **판정과 종료 코드**만 보고 다음 행동을 정합니다.

## 2. 판정 결과에 따른 행동

| 종료 코드               | 의미             | 행동                                                                                                                            |
| ----------------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 0                       | ✅ 통과          | 사용자에게 한 줄 보고 후 다음 Phase로                                                                                           |
| 1                       | ❌ 실패          | 실패 항목과 복귀 게이트를 사용자에게 보고하고, `next`(복귀 게이트)의 에이전트를 실패 사유와 함께 다시 호출                      |
| 1 (p3-approval, ⏳)     | 컨펌 대기        | 3번으로                                                                                                                         |
| 1 (P4·P5 → p3-approval) | 컨펌 잠금 무효   | 승인 뒤 설계·시안이 바뀌었거나 잠금 기록이 없음. 사용자에게 보고하고 `judge` → `p3-approval`(기존 컨펌이 보관되고 ⏳) → 3번으로 |
| 2                       | 사용법·전제 오류 | 멈추고 오류를 그대로 보고                                                                                                       |
| 3                       | 🛑 차단          | **즉시 멈추고** 7번 보고. 스스로 재시도하거나 unblock 하지 않음                                                                 |

## 3. 사람 승인 지점 (P3 → P4, 이 하네스의 유일한 사람 승인)

1. P3 게이트 통과 후 멈추고 사용자에게 알립니다:
   - 시안 목록(링크 · 노드 ID)과 `harness/templates/approval.md` 양식 위치
   - "내부 관계자 컨펌 후 `runs/<slug>/p3-concept/approval.md`를 작성해 주세요."
2. **오케스트레이터와 에이전트는 approval.md를 작성하지 않습니다.**
   - 사용자가 채팅으로 결과를 말하더라도("A로 컨펌 받았어") 파일은 사용자가 직접 작성하도록 안내합니다.
3. 사용자가 작성을 알리면 `judge` → `p3-approval`
   - 승인 → P4로 · 반려 → 스크립트가 반려본을 보관하고 P2로 복귀 (spec-writer에게 반려 코멘트 전달)
4. **컨펌 잠금**: 승인 시점의 screen-spec·concepts·approval.md 해시가 `state.json`에 기록됩니다.
   - reopen 뒤 설계나 시안이 바뀌었으면 예전 approval.md는 `approval-stale-<n>.md`로 보관되고 ⏳ 컨펌 대기가 됩니다. 사용자에게 사유와 함께 "현재 설계·시안으로 다시 컨펌받아 approval.md를 작성해 주세요"라고 안내합니다.
   - 바뀐 것이 없으면 기존 컨펌이 그대로 인정됩니다.

## 4. 완료

`p5` 통과(`state.json`의 `done: true`) 시 보고:

- 화면 목록 S1~Sn 각 프레임 링크, `runs/<slug>/p5-flow/verify-report.md` 요약 (커버리지 포함)
- 완료 기준 확인: 화면 목록의 **모든 화면**이 390×844 완성본 · 커버리지 누락 0건 · design.md 위반 0건 · ★ 위반 0건 · 내부 컨펌 완료

## 5. 상태만 물을 때

"하네스 상태 알려줘" → `node harness/scripts/verify.mjs status <slug>` 결과만 보여주고 아무것도 진행하지 않습니다.

## 6. 금지

- 저장 권한은 hook(`harness/scripts/guard-write.mjs`)이 강제합니다: runs/ 안에서는 현재 게이트 폴더에만 저장되고, state.json·verify-report.md·approval.md 쓰기와 서브에이전트의 쓰기는 막힙니다. 막히면 우회하지 말고 사용자에게 보고합니다. Bash로 runs/ 파일을 쓰는 것도 하지 않습니다.

- 에이전트가 반환한 산출물 내용을 고치거나 오케스트레이터가 산출물을 새로 작성하지 않습니다. (게이트 실패 시에도 수정은 해당 에이전트에게 다시 맡깁니다)

- `state.json`, `verify-report.md`, `harness/rules.yaml`을 직접 수정하지 않습니다.
- 게이트를 건너뛰거나 판정을 해석으로 뒤집지 않습니다.
- `unblock`은 사용자가 명시적으로 요청할 때만 실행합니다.

## 7. 🛑 3회 실패 보고 형식

```
🛑 하네스 중단 — <gate> 게이트 3회 연속 실패
실행: runs/<slug>  (주제: <주제>)
실패 이력: (state.json history의 해당 게이트 실패 3건 요약)
반복된 원인: (공통 위반 항목)
선택지: ① 산출물 직접 수정 후 unblock ② rules.yaml 기준 조정 ③ 이 주제 중단
```
